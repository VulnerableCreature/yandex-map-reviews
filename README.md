## Как поднять локально

```bash
cd ..
docker compose up -d --build

docker compose exec app php artisan migrate --seed
docker compose exec app php artisan storage:link
```

Приложение:
- Frontend (SPA): http://localhost:5173
- Backend (API): http://localhost:8000

Данные для входа логин: **admin@example.com** пароль: **password**

Очередь обрабатывается отдельным контейнером `queue-worker`

## Подход к парсингу

Используется обычный HTTP-клиент Guzzle и внутренние запросы Яндекс.Карт.

Сначала проверяется ссылка организации. Обычная ссылка нормализуется, а короткая ссылка вида `/-/CODE` разрешается через HTTP-редирект. После этого определяется `permalink`.

Данные организации берутся из HTML страницы карточки: название, рейтинг, количество оценок и количество отзывов.

Отзывы загружаются через внутренний `fetchReviews`. Парсер получает необходимые cookies и `csrfToken`, после чего запрашивает отзывы страницами.

Прогресс парсинга сохраняется в `parsing_jobs`.

Количество загружаемых отзывов ограничено примерно 600 записями.

# Обоснование подхода (JSON API)
**Почему выбран JSON API:** по ТЗ надо 600 и сам яндекс отдаёт +- до 600 отзывов поэтому нам нужно получать относительно
небольшое количество отзывов и филиалов, поэтому HTTP-запросы к API проще выполнять, чтобы получить данные, но API может измениться, 
и парсер перестанет работать поэтому есть проверка структуры полученных данных чтобы, исправить парсер.

## 1. Фоновая обработка

Парсинг реализован через очередь, а не синхронно в HTTP-запросе:

- `OrganizationController::store()` вызывает application service, который сохраняет ссылку и **диспатчит**
  `ParseOrganizationReviewsJob` в очередь (`QUEUE_CONNECTION=redis`), сразу возвращая `202`.
- Прогресс пишется в отдельную таблицу `parsing_jobs` (`reviews_fetched`,
  `reviews_total_estimate`, `status`) колбэк `onProgress` в `YandexMapsParserService` обновляет
  её на лету, по мере вытягивания страниц.
- Повторные попытки при сбое через штатный стандартный Laravel Queue: `tries = 3`,
  `backoff = [30, 120, 300]` секунд (нарастающая пауза, чтобы не долбить источник сразу после
  ошибки). `markup_changed` исключение из этого правила
- Отдельный контейнер `queue-worker` в `docker compose.yml`

## 2. Анти-бан на объёме

Реализовано:
- **Троттлинг** между запросами страниц отзывов одной организации настраиваемая пауза
  (`YANDEX_MAPS_THROTTLE_MS`) чтобы не долбить пачкой запросов подряд.
- **Ротация User-Agent** — список в `config/services.php`, случайный выбор на каждый запрос.
- **Нарастающий бэкофф при сбое** через очередь, а не мгновенный повторный запрос.

## 3. Идемпотентность и история изменений

- Уникальный индекс `(organization_id, external_id)` на `reviews` + `Review::updateOrCreate()`
  в `ReviewRepository::upsertBatch()` повторный парсинг той же организации **не создаёт
  дублей**, существующие отзывы обновляются на сразу.
- Для каждого отзыва хранится `content_hash` (sha256 от автора+оценки+текста+даты) по нему
  считываются был ли отзыв **новым** или **изменившимся** за этот запуск
- Таблица `review_snapshots` — один снимок агрегатов (рейтинг/число оценок/число отзывов) и
  диффов (`reviews_added`, `reviews_updated`, `reviews_removed`) **на каждый запуск парсинга**,
  привязанный к конкретному `parsing_job_id`.

## Что доделал бы, имея больше времени

- Тесты: юнит-тесты на `YandexMapsUrlValidator` и `ReviewRepository::upsertBatch` (идемпотентность),
  фиче-тест на `OrganizationController::store` с замоканным парсером.
- Алертинг Telegram-вебхук или Sentry при статусе `markup_changed`, чтобы узнавать о поломке
  парсера сразу, а не по логам.
- UI: индикатор процента прогресса парсинга (`reviews_fetched` / `reviews_total_estimate` уже
  есть в `parsing_jobs`, не хватает только прогресс-бара на фронте) и сортировка/фильтр отзывов
  по оценке.
